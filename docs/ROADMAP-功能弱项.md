# 功能弱项弥补路线图（2026-11）

> 记录三个已知短板的技术现状、可行方案和工作量。写这个是为了避免「凭感觉说要强化」——每条都要说清楚**能不能做、怎么做、代价是什么**。

## 一、Cookie 自动导入（从浏览器直接读，用户只点一次批准）

### 技术现状（2026-11 实测）

| 浏览器 | 可行性 | 原因 |
|---|---|---|
| **Firefox** | ✅ 完全自动 | Cookie 存在明文 SQLite（`%APPDATA%\Mozilla\Firefox\Profiles\*\cookies.sqlite`），无加密，复制文件即可读 |
| **Chrome / Edge** | ⚠️ 只能靠 CDP | 127 版（2024-07）起启用 **App-Bound Encryption**：解密密钥绑定浏览器自身进程，外部程序（**包括管理员权限**）都无法解密 |
| Safari | macOS 可行 | 需要「完全磁盘访问权限」 |
| 其它 Chromium 系 | 同 Chrome | Brave、Vivaldi、Opera 一样受限 |

关键事实：**Chrome/Edge 的 Cookie 数据库复制出来是一堆 `v20` 开头的密文**，这不是权限问题，是设计上就不给外部进程解。网上那些「提权就能读」的方案在 127+ 之后全部失效。

### 可行方案

**阶段一：Firefox 全自动（工作量 小，1-2 天）**
1. 扫描 `%APPDATA%\Mozilla\Firefox\Profiles\`，按 `cookies.sqlite` 大小挑主配置
2. 复制到临时目录（Firefox 会锁原文件），`sqlite3` 读 `moz_cookies`
3. 转成 Netscape 格式写入 `cookies/<站点>.txt`
4. 界面上一个「从 Firefox 导入」按钮，点一下完事

**阶段二：Chrome/Edge 走 CDP（工作量 中，3-4 天）**
1. 提示用户「需要关闭浏览器一次」，点确认
2. 用**用户的真实配置目录**启动一个带 `--remote-debugging-port` 的实例
3. 连 CDP → `Network.getAllCookies`（浏览器自己解密，拿到明文）
4. 筛选目标域名写入 cookies 文件
5. 关掉这个实例，提示用户可以重新打开浏览器

**这条路的限制要说清楚**：必须关闭浏览器（不关的话新进程会把请求转交给已有实例，调试端口不生效）——所以「完全无感」做不到，只能做到「点两下代替手动导出」。

**阶段三：兜底不删（现有方式保留）**
扩展导出 `cookies.txt` 仍然保留，作为 CDP 失败时的退路。

### 不建议做的事
- ❌ 不内置 Chrome 扩展（要上架、要维护、用户还得装）
- ❌ 不尝试破解 App-Bound Encryption（那是 google 专门防恶意软件的机制，破解等于写恶意软件）

## 二、优酷 / 腾讯 / 爱奇艺（必须先把边界说清楚）

### 先划两条线

**线一：DRM 加密内容 —— 不做，也不会做。**

会员片、付费内容是 Widevine / ChinaDRM / PlayReady 加密，解密需要内容密钥，而密钥由许可证服务器在播放时下发。绕过它属于**规避技术措施**：

- 《中华人民共和国著作权法》第四十九条明确禁止规避技术措施
- 美国 DMCA §1201 同理
- 本项目的 LICENSE 也写明「不绕过 DRM」

所以像 `yt-dlp-MP4decrypt` 这类工具，定位是**给「你自己拥有密钥的加密文件」做解密**（企业自有内容、自己加密的素材），不是拿来解平台 DRM 的。用它下载会员片，风险在你自己身上，我不会协助。

**线二：非 DRM 的「下载受限」—— 可以认真处理。**

这些站点的免费内容不是 DRM，而是**防盗链 + 接口签名 + 设备指纹**，属于反爬。技术上能不能过是另一回事，但性质不同。

### 三个平台的真实情况（2026-11）

| 平台 | yt-dlp 现状 | 受限原因 | 可做的事 |
|---|---|---|---|
| **优酷** | 有 extractor，**只对免费内容有效** | 接口签名 + Cookie 校验 + 部分地区限制 | 升级 yt-dlp、补 Cookie（会员 Cookie 能解免费内容的地区限制）、换出口 IP |
| **爱奇艺** | 有 extractor，**只对免费内容有效** | 同上，另有 `qsv`/`ts` 分片加密 | 同上；部分内容需要 `--extractor-args` 指定客户端 |
| **腾讯视频** | **没有 extractor** | 接口完全私有 | 短期无解。要么等社区补 extractor，要么放弃 |

腾讯视频这条要现实一点：**yt-dlp 至今没有它的提取器**，不是配置问题。想做只能自己逆向它的接口——工程量以月计，且随时失效，我不建议投入。

### 建议的落地动作（按性价比排序）

1. **先确认失败原因再动手**（工作量 小）：现在下载失败时，日志里是 403、超时、还是"no video formats found"？三种原因对应完全不同的处理。→ 加一个「诊断」按钮，把 yt-dlp 的关键日志行提取成人话。
2. **补齐 Cookie**（工作量 小）：优酷/爱奇艺免费内容加会员 Cookie 后成功率明显提升。这条依赖上面的「Cookie 自动导入」。
3. **跟随 yt-dlp 升级**（工作量 小）：extractor 修复上游一直在做，升级本身就解决一部分。
4. **腾讯视频单独立项评估**（工作量 大，建议搁置）。

## 三、画质偏低（已定位并修复一半）

### 真正的原因（已修）

`yt-dlp` 从 2026 年起要求 **JS 运行时**来解 YouTube 的 `n-challenge`（nsig）。没有运行时的表现**不是报错**，而是：格式列表被砍到只剩 storyboard（图片）或低清版本——非常容易被误判成「这站只有低画质」。

本项目之前的问题更隐蔽：**探测到了 Node，但传参格式错了**。

```
错误写法：--js-runtimes "C:\Program Files\nodejs\node.exe"
yt-dlp 按「冒号前是运行时名」解析 → 拿到 "C" → 不认识 → 静默忽略
正确写法：--js-runtimes "node:C:\Program Files\nodejs\node.exe"
```

已改为 `RUNTIME:PATH` 格式。实测输出从

```
[jsc] JS Challenge Providers: bun (unavailable), deno, node (unavailable), quickjs (unavailable)
```

变成

```
JS runtimes: node-22.22.2
[jsc:node] Solving JS challenges using node
```

### 还能继续做的

1. **Deno 作为首选**（工作量 小）：yt-dlp 默认只启用 deno。Deno 单文件、约 40MB，可以随程序分发到 `bin/`，用户什么都不用装。Deno 在 JS 挑战上的兼容性比 Node 更稳（yt-dlp 官方推荐）。
2. **PO Token 提供方**（工作量 中）：部分客户端（mweb/ios）要求 Proof-of-Origin Token，没有的话格式会少一批。可选装 `bgutil-ytdlp-pot-provider`，但它需要常驻服务，会明显增加复杂度——建议先观察 Deno 是否够用。
3. **格式选择策略**（工作量 小）：同一分辨率下 HLS 和 DASH 码率能差 7-9 倍，默认选择器可能挑到低码率那条。可以在「最高画质」选项里显式偏好 `m3u8`，并在拿不到时逐级兜底。
4. **诊断入口**（工作量 小）：把 `-F` 的格式列表做成可展开的面板，用户能自己看到「到底有哪些格式、被谁过滤了」。

## 优先级建议

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | 画质：Deno 随包分发 + 格式选择优化 | 已完成一半，剩下的改动小、收益直接 |
| P1 | Cookie：Firefox 全自动导入 | 纯增量，风险低，能明显提升 B站/优酷成功率 |
| P2 | 下载诊断按钮 | 让「为什么失败」可见，减少瞎猜 |
| P3 | Cookie：Chrome/Edge 走 CDP | 有价值但体验有妥协（要关浏览器），ROI 一般 |
| P4 | 腾讯视频支持 | 无 extractor，工程量与风险都不成比例，建议搁置 |

## 明确不做

- 破解 DRM（Widevine / ChinaDRM / PlayReady）
- 破解 Chrome App-Bound Encryption
- 绕过付费墙、会员权益、地区版权限制
- 提供「解析网站」式的第三方接口硬编码

理由不是技术做不到，是这四条都越过了「工具」和「侵权工具」的界线。这个项目的许可里也写明了。
