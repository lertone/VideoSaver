# yt-dlp 生态调研与 VideoSaver 定位（2026-11）

> 目的：搞清楚这个项目在整个生态里处于什么位置，别人做对了什么，哪些值得学、哪些不值得。

## 一、生态分层

所有工具都跑同一个引擎（yt-dlp 2026.10.26，1734 个提取器，其中 136 个当前标记为失效）。差别不在"能不能下"，而在**外壳形态**和**下载之后做什么**。

| 层 | 代表 | 强在哪 | 代价 |
|---|---|---|---|
| 引擎 | yt-dlp | 覆盖 1700+ 站点，更新最勤 | 命令行 |
| 桌面 GUI | Open Video Downloader（9.6k）、Parabolic、Stacher（闭源付费）、Tartube | Stacher 几乎每个 flag 都有 UI；OVD 平衡；Parabolic 最像原生 Linux 应用 | 本质是「参数翻译器」 |
| 移动 | Seal（Android，30k+） | 手机端唯一成熟方案 | 只有 Android |
| 自托管/归档 | MeTube（13.8k）、TubeArchivist（8.1k）、PinchFlat（5k）、ytdl-sub（2.8k） | 订阅频道、定时拉新、喂 Jellyfin | 要跑 Docker；TubeArchivist 光 ES 就吃 4GB |
| 创作流水线 | ViralMint（闭源商业） | 下载 → Whisper 转写 → AI 切片 → 字幕 → 竖屏 | 按订阅收费 |

### 三个被反复验证的行业事实

1. **所有工具同时失效**。2026 年 2 月 YouTube 的 LOGIN_REQUIRED 风控墙，把上面每一款同时打挂。谁也没有绕过引擎层的护城河。
2. **Cookie 是行业级痛点**。Chrome 127+ 的 App-Bound Encryption 让所有工具的外部读取全部失效，**Firefox 是 2026 年唯一可靠的来源**；导出的 cookie 约两周过期。
3. **无人值守需要 POT provider**。YouTube 的 Proof-of-Origin 令牌要常驻服务（bgutil-ytdlp-pot-provider），不做就只能半自动。

## 二、VideoSaver 现在算什么档位

**老实说：第三梯队的功能广度，第二梯队的完成度，但有一个别人没有的组合。**

| 维度 | 评价 |
|---|---|
| 引擎覆盖 | 与所有 GUI 相同（都用 yt-dlp），无差异 |
| Flag 覆盖度 | 不如 Stacher（它是"每个参数都有勾选框"的极致） |
| 订阅/归档 | **没有**（Tartube / PinchFlat / ytdl-sub 的主场） |
| 移动端 | 没有 |
| 媒体库集成 | 没有（无 NFO、无 Jellyfin 结构） |
| 知名度 | 几乎为零（星标、用户量都不构成竞争力） |

**但它有三件别人没做的事**：

1. **AI 助手能真正操作文件** —— 别的工具最多帮你下载；这里的助手能读懂「把上周那批舞蹈视频按内容重命名，然后归档到 2025-11」。Stacher 下载完就结束了，这里下载完才是开始。
2. **嗅探带登录态** —— 独立浏览器 profile + Cookie 注入，能抓需要登录才出流的地址。这笔功能在主流 GUI 里基本没有（它们只接受粘贴 URL）。
3. **中文本地化 + 本地优先** —— 没有账号、没有遥测、配置和 Cookie 全在本机。海外工具不做中文场景（B站、抖音、小红书、优酷），国内工具又大多不做工程化。

**一句话定位**：不是「下载器」，是**下载之后的本地媒体管家**。赛道其实和 Stacher 不同，更接近「Tartube 的归档思路 + 一个能干活的助手」。

## 三、值得借鉴的（按投入产出排序）

### P0：失败自动重试 + Cookie 刷新闭环
ViralMint 的做法值得抄思路：403 时不是报错，而是**自动换策略重试**（刷新 cookie → 换客户端 → 换格式档位）。
本项目的失败提示已经能说人话，但**没有自动恢复**。改成：识别错误类型 → 依次尝试 `换 cookie` / `降档` / `换 client` → 全失败才报错。这是体感提升最大的一项。

### P1：订阅与增量拉新
PinchFlat 的过滤器是同类最全的：标题正则、发布日期截止、时长区间、Shorts/直播开关、**dry-run 预览**。
本项目不需要做成常驻服务，只要「保存一条订阅 → 点一次检查 → 只下新的」（用它自己的 `--download-archive` 记账即可）。这能覆盖「追更某个 UP」的高频场景，且实现成本不高。

### P1：Whisper 转写（本地或走已有 AI Key）
ViralMint 把「下载 → 转写 → 切片」做成一条流水线，本质是把下载当第一步。
本项目已有 AI 助手，缺的是**音频转文字**这一步。两条路：本地 faster-whisper（模型 200MB 起，离线但要打包）或调用户自己的 AI Key（零体积，需联网）。这直接把「素材」变成「可检索的文本」，和现有的搜索/归档能力天然衔接。

### P2：POT provider 内置
如果要做无人值守（订阅、定时），YouTube 的 PO Token 绕不过去。可以把 bgutil 的方案做成可选组件，默认关闭。不做的话，订阅功能在 YouTube 上会三天两头失效。

### P2：媒体库友好的输出（NFO + 目录结构）
PinchFlat / ytdl-sub 的价值在于「下完就能被 Jellyfin 认出来」。
本项目可以把「保存目录」扩展成可选的 `TV Show / 季 / 集` 结构并生成 NFO。只在用户勾选「媒体库模式」时生效，不影响现有扁平结构。

### P3：任务队列的并发与断点
MeTube 的队列是它 13.8k 星的主要来源：多任务排队、暂停、恢复、并发数控制。
本项目现在是单任务流。做队列的价值中等（个人用户很少同时下五个），但**断点续传的可见性**值得做——现在断了只显示失败，用户不知道能不能续。

## 四、明确不学的东西

| 不学 | 原因 |
|---|---|
| TubeArchivist 的三容器架构 | 为一个桌面工具引入 Elasticsearch + Redis，运维成本与收益完全不匹配 |
| Stacher 的「全 flag UI」 | 参数有几百个，全暴露等于把 CLI 换个皮，反而更难用 |
| 闭源 + 付费墙 | 本项目已有非商业许可，走的是另一条路 |
| 任何 DRM 绕过 | 法律边界，见 [ROADMAP-功能弱项](ROADMAP-功能弱项.md) |

## 五、结论

如果按「下载能力」排，这个项目**排不进前列**，也不该往那个方向卷——引擎是共用的，卷参数没有护城河。

真正的机会在**下载之后**：Stacher 给文件，Tartube 给归档，ViralMint 给创作，而这里能给的是**一个能读懂需求、直接动文件的助手**。这条路上目前没有像样的竞品，因为其他工具的作者没有把 AI 当成一等公民，只是加了个「AI 摘要」的按钮。

所以下一步的最优解不是加更多下载参数，而是：
1. 让失败能自愈（P0）
2. 让「追更」变成一条命令（P1）
3. 让音频变成可搜索的文本（P1）

这三件事都在「下载之后」，也正是这个项目唯一可能建立差异化的地方。
